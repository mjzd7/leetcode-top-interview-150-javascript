Design a Rate Limiter

A rate limiter is a bucket with a rule attached. One of the most asked system design questions at every tier, and the only one where the interviewer grades whether you understand failure as much as flow. This page carries the important parts: the five algorithms, the distributed shape, the atomicity problem, the 429 contract, the failure modes that actually page you at 3am — then 50 questions interviewers actually ask about it.

01TL;DR + analogy

The bucket with a hole in it. A reservoir drips water into your bucket at a fixed rate (the refill rate). Your bucket has a maximum size (capacity). Every request spends one unit from the bucket. If the bucket is empty, the request is rejected with 429. A tall bucket lets you save up credit while idle and then spend it in one burst — that is why token bucket is the default choice for APIs: it smooths the average rate without punishing bursts.

Two knobs and they mean completely different things, which is the single most misunderstood point in every interview: capacity controls burst, refill rate controls sustained throughput. A bucket of 100 refilling at 1/s allows 100 requests instantly and then exactly 1/s forever after. An interviewer who hears "rate limit of 100" and does not hear which of the two you mean will assume you do not know.

The whole system is three things: a key (whose bucket — user, IP, API key, tenant, endpoint), an algorithm (how tokens are counted), and a decision (allow or 429). Everything else is plumbing. Interviewers score the first three, then hunt the plumbing.

02Why companies care

Abuse + DoS

The cheapest defence you can put in front of a database. A scraper issuing 50k req/s does not get to choose how much of your database it eats.

Cost control

Every third-party call costs money. A runaway retry loop from one customer is your AWS bill. Limits make spend predictable per tenant.

Cascading failure

A slow dependency turns into a queue, a queue turns into memory exhaustion, and every other endpoint on the box dies with it. A limiter plus load shedding is what keeps one sick dependency local.

Fairness + quotas

Free tier gets 10 rpm, enterprise gets 1000. Same code path, different bucket size — the limit is the product tiering.

Downstream protection

Stripe, OpenAI, your own ML inference box all publish limits. Your limiter is the shim that makes you a well-behaved client instead of a banned one.

Revenue + product

Concurrency caps protect expensive resources; signup / post / claim / coupon endpoints are rate limited specifically because they are abusable and directly tied to money.

03Where does it live

The interviewer's tell: if you place the limiter only at the edge, you have not protected anything downstream that is also reachable internally, and a single bug in your key extraction (IPv6 rotation, NAT, proxies) lets one attacker hold many buckets. Placement question they will always ask — "where does this run, and what happens to the limits if that component is down?"

04The five algorithms

Memorising five names is worthless. What you must be able to do is draw the shape of each one and name the specific failure it fixes and the specific cost it introduces. That is the whole question.

4.1 Token bucket default answer

  • Parameters: capacity (burst ceiling) and refill rate (sustained rate). Also cost per request — a search endpoint can cost 10 tokens, a health check 1.
  • Pros: absorbs bursts up to capacity, enforces a hard long-run average, O(1) memory per key (two numbers), trivial to reason about and to explain.
  • Cons: two knobs to tune, no smoothing of output (a burst is let through instantly), and an idle-then-return user gets a full bucket.
  • Use when: API gateways, payment/auth endpoints, LLM APIs, anything with legitimate burstiness. This is what AWS API Gateway and Stripe use.

4.2 Leaking bucket

Same rate, opposite philosophy: instead of allowing bursts, it smooths the outflow. Requests go into a FIFO queue; a worker releases them at exactly R per second. Memory stays O(1) because you only hold the queue head plus a timer.

  • Pros: perfectly smooth output rate — protects a downstream that cannot absorb spikes (a warehouse robot, a payment processor, a batch job).
  • Cons: adds queueing latency; a burst gets delayed rather than served; queue overflow needs a policy (reject newest vs reject oldest vs grow) and that policy is itself a design question.
  • Use when: the downstream has a hard physical rate limit. Uber's open-source Go ratelimit is a rate smoother of this family — a good thing to have read.

4.3 Fixed window counter

  • Pros: one counter per key, O(1), trivially cheap — the right answer for coarse internal limits.
  • Cons: the 2× boundary burst above; also not smooth inside the window.
  • Use when: quota is a business entitlement (1000/day) rather than a protective rate. Then the boundary burst does not matter.

4.4 Sliding window log

The accurate one: store the timestamp of every accepted request in a sorted set (Redis ZSET), and on each request drop everything older than now − window then count what remains. Perfectly correct rolling window, no boundary, no approximation.

  • Pros: exact; no boundary artifact; naturally supports "log of what was allowed" for audit.
  • Cons: memory O(requests in window) — at 10k req/s/user that is 600k entries; plus ZREMRANGEBYSCORE + ZCARD + ZADD per request.
  • Use when: high-value, low-volume endpoints (payments, login attempts, coupon claim) where accuracy beats memory.

4.5 Sliding window counter

The pragmatic compromise, and the answer that reads as "I know the tradeoffs". Keep the current window's count and the previous window's count; estimate the rolling window as current + previous × (1 − fractionElapsed). Constant memory per key, and the 2× boundary burst collapses to ~1.5× worst case in the pathological case, tunable by keeping 2 or 3 sub-windows.

  • Pros: two integers per key, O(1), smooths the boundary.
  • Cons: an approximation — it can still admit slightly more than the true quota; you must state that honestly rather than claiming it is exact.
  • Use when: high-throughput general-purpose API throttling. Most production systems land here.

Say this out loud in the interview: "I'd start with token bucket because it handles bursts, which is how real traffic behaves, and because it costs two integers per key. If the requirement is 'no more than 10 per second ever, smoothly', I'd switch to a leaky bucket. If it's a hard security boundary like login attempts, I'd pay for the sliding log. If it's a monthly plan quota, fixed window is enough." Naming when you would change your mind is the difference between a candidate who memorised and one who designs.

07Atomicity: the actual hard part

Naive limiter: GET counter, if under limit then INCR. In a single process with one thread that is fine. Everywhere else it is broken, and the bug is not subtle — it is a classic time-of-check-to-time-of-use race. Two requests arrive at the same instant, both read 499 with a limit of 500, both conclude "allowed", both increment → 501 requests went through a 500 limit. At scale you do not get 1% overshoot, you get a proportion of your peak QPS overshoot.

The three ways to fix it, and what each costs.
1. INCR then check — atomic in one command, but the counter is already incremented when you reject, so a client hammering you inflates its own penalty and, with multiple keys, you get partial tiers consumed on a request you then reject.
2. Distributed lock around read-modify-write — correct but you now have a lock service in your hot path, a lock-expiry failure mode, and a latency hop.
3. Lua script / Redis Function — the whole read-refill-check-write runs inside Redis, single threaded, indivisible, one round trip. This is the answer to give.

Say the words "check and decrement must be atomic, and Redis executes a Lua script as one indivisible operation, so the whole decision is a single round trip". Interviewers are listening for exactly that sentence. Then mention the cluster caveat yourself — it is the follow-up they were already going to ask.

08Code

Token bucket in Lua (the production answer)

-- KEYS[1] = rl:{tenant}:user:42
-- ARGV[1] = capacity   (burst ceiling)
-- ARGV[2] = refill rate, tokens per second
-- ARGV[3] = cost of this request
-- ARGV[4] = now, ms  (passed in: never trust the client's clock)
-- returns { allowed, remaining, retry_after_ms }
local capacity, rate, cost, now =
  tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])

local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now

local elapsed   = math.max(0, now - ts) / 1000          -- negative = clock went backwards
local refilled = math.min(capacity, tokens + elapsed * rate) -- cap: idle time is not free credit

local allowed, retry_after = 0, 0
if refilled >= cost then
  tokens = refilled - cost
  allowed = 1
else
  tokens = refilled
  retry_after = math.ceil((cost - refilled) / rate * 1000) -- honest Retry-After, not a guess
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- key can die once a full bucket's worth of refill time has passed
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)
return { allowed, math.floor(tokens), retry_after }

Four details that separate a real implementation from a toy: (1) pass now in from the caller so every node agrees; (2) clamp elapsed to ≥ 0 so an NTP step backwards cannot mint free tokens; (3) cap refill at capacity so an hour-idle key does not become a huge burst; (4) compute Retry-After from the deficit so the client's backoff is correct instead of a guess.

Sliding window log in JS (accuracy where it matters)

// login attempts: exact rolling window, bounded memory by capping the log
const Lua = `
local k, now, win, cap = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', k, '-inf', now - win)   -- drop expired
local n = redis.call('ZCARD', k)
if n >= cap then return {0, n, now + win - redis.call('ZRANGE', k, 0, 0, 'WITHSCORES')[2]} end
redis.call('ZADD', k, now, now)
redis.call('PEXPIRE', k, win)
return {1, n + 1, 0}`;

async function allow(key, { limit, windowMs }) {
  const now = Date.now()
  const [allowed, remaining, retryAfter] =
    await redis.eval(Lua, 1, key, now, windowMs, limit)
  return { allowed: allowed === 1, remaining, retryAfter }
}

Node-side middleware, JS-flavoured, same contract — note how the response is built from the limiter's decision rather than the middleware inventing numbers. 

import { RateLimiter } from './limiter.js'

const limiter = new RateLimiter({ capacity: 100, refillPerSec: 10, cost: 1 })

export async function rateLimitMiddleware(req, res, next) {
  const key = `rl:{${tenantOf(req)}}:${routeClass(req)}:${identityOf(req)}`
  const { allowed, remaining, retryAfter } = await limiter.take(key)

  res.set('RateLimit-Limit', limiter.capacity)
  res.set('RateLimit-Remaining', remaining)
  res.set('RateLimit-Reset', Math.ceil((Date.now() + retryAfter) / 1000))

  if (!allowed) {
    res.set('Retry-After', Math.ceil(retryAfter / 1000))
    return res.status(429).json({
      error: { code: 'rate_limit_exceeded', retryAfter: Math.ceil(retryAfter / 1000), scope: routeClass(req) }
    })
  }
  next()
}

09The 429 contract

A rate limiter that rejects without telling the client how to behave is a bug. This section is pure scoring: almost every real API exposes some variant of these headers, and naming them unprompted is a cheap way to look like you have shipped one.

HeaderMeaningNote
429Too Many Requests (RFC 6585)the only correct status for throttling — not 503, not 403
Retry-Afterseconds (or HTTP-date) to waittakes precedence over any reset header when both present
RateLimit-Limit
-Remaining
-Reset		IETF draft standard namessend on every response, not only 429, so clients can self-throttle
X-RateLimit-*legacy de-facto namesstill what most APIs ship; harmless to send both
RateLimit-Scopewhich limit tripped: api-key / organization / iptells the client whether to slow down or split its keys
RateLimit-Resetepoch seconds when capacity returnsnever a duration — clients compute wrong if you send "60"
  • Body: machine-readable code + retry hint. Modern APIs return application/problem+json (RFC 9457) with type, title, status, plus your own retry_after and scope.
  • Include the limit that actually tripped when several scopes apply, otherwise clients cannot tell whether to retry slower or get a bigger plan.
  • Client guidance you should be able to state: honour Retry-After, add jitter (10–30%) so a fleet does not retry in lockstep, cap attempts, pre-emptively slow down when Remaining/Limit < 10%, and send an idempotency key on retried writes so a retry never double-charges.

11Failure modes

This is the section that separates SDE-2 from SDE-1 answers, and it is where the chapter is thin in most notes. If you only add one thing to your preparation, add this.

FailureSymptomAnswer

Related but distinct — load shedding and backpressure. Rate limiting caps rate; shedding drops work when the system is already overloaded; a circuit breaker stops calling a sick dependency at all; a queue absorbs the difference. Interviewers love a candidate who can say "this is a rate limiter, not a circuit breaker — for the sick-downstream case I would add a breaker here and shed excess load here", and can sketch client-side adaptive throttling (slow down when the server's accept queue grows) as the client-side complement to all of it.

12How to narrate the round (45 min)

TimeDo thisSay
0–8 minScope it. Write assumptions down."Who is limited — IP, user, API key, tenant? Which endpoints? What happens on exceed — 429, queue, or drop? What is the limit, per what window? Is it global across regions?"
8–15 minEstimate, then pick placement + algorithm out loud."At 6k QPS peak with 10M active identities, token bucket state is ~1 GB, so Redis sharded is comfortable; sliding log would be hundreds of GB — rejected."
15–30 minDraw the box diagram, then deep dive on atomicity."Check-and-decrement must be atomic. GET then INCR races; a Lua script makes it one indivisible op."
30–40 minDeep dive on failure — Redis down, retry storms, hot keys. This is where senior candidates win."If Redis is unavailable I fail open for reads and closed for payments, with a local fallback and an alert."

What is actually graded: whether you ask before you build, whether your numbers are ordered correctly, whether you found the race condition, whether you raised a failure mode nobody asked about, and whether you said "I don't know, here's how I'd find out" instead of bluffing. Nobody grades your box count.

13Top 50 questions on rate limiting in system design

The chapter's content, turned into the questions an interviewer actually asks. Grouped by what they are testing. Open any row for the answer that gets you through it.

A · Scope and requirements (1–8) asked first, always

1Design a rate limiter for our API.the canonical prompt
Requirements → placement → algorithm with justification → data model → atomicity → failure modes. Follow §12 for the clock. The prompt is deliberately underspecified; the first 5 minutes are the question.
2Who do we limit — IP, user, API key, or tenant?key design decision
Almost always layered: per-IP (cheap abuse shield) → per-user (fairness) → per-tenant/org (billing) → global (protect the system). First scope to trip returns 429 and you report which via RateLimit-Scope. IP alone is defeated by proxies and botnets; user alone needs auth before you can rate limit, so it cannot protect the login endpoint.
3What happens when the limit is hit — reject, queue, or downgrade?reveals product thinking
Reject with 429 for APIs (cheap, standard, client-fixable). Queue when the work is deferrable and the queue is bounded (with an explicit overflow policy). Downgrade — serve a cached/stale response — when the endpoint is a read and freshness does not matter. Never silently drop.
4Multiple limits on one endpoint: 10/s and 1000/day. How?composite policies
All tiers evaluated in one atomic script that returns the first violation and its scope — otherwise a client can consume its daily quota on requests you later reject. Different algorithms per tier is fine: token bucket for the burst, fixed window for the day.
5Per-route limits — how do you avoid a config explosion?abstraction judgement
Bucket classes (read-light / write-light / expensive / long-running) and assign routes to classes, rather than per-route numbers. Tier × class × scope is a small matrix. Publish the class on the response so clients can reason about it.
6Rate limit vs quota vs concurrency limit — what's the difference?precision
Rate = requests per window (throughput). Quota = total volume per period (an entitlement/billing concept, often a daily or monthly counter). Concurrency = in-flight requests right now. They are three different dimensions and a real design needs all three: rate protects throughput, concurrency protects expensive resources from slow clients.
7Should limits differ per plan tier?product/billing awareness
Yes, and it is the same code path with a different capacity and rate — which is the strongest argument for token bucket, since the two knobs map to burst and sustained throughput independently. Exceeding a monetary quota is sometimes 402, not 429 — a billing boundary rather than a throttle.
8How do you pick the numbers?data, not vibes
From capacity math: what does one unit of downstream resource cost, what does the system sustain, and what fraction is safe for one tenant? Start permissive in shadow mode, watch the distribution, then tighten. Never ship a guessed limit to 100% of traffic on day one.

B · The five algorithms (9–20) the graded core

9Explain token bucket.must be instant
Tokens added at a fixed rate up to a capacity; each request spends some; empty → reject. Capacity = burst allowed, rate = sustained average. Lazy refill: compute accrual from elapsed time at request time, no timer.
10Explain leaky bucket and when it beats token bucket.distinguishes memorised from understood
FIFO queue drained at a constant rate — output is smooth, bursts are delayed not served. Choose it when the downstream has a hard physical rate limit you must not exceed, and you would rather add latency than shed load.
11What is the fixed-window boundary problem?the classic gotcha — volunteer it
A client sends its full quota at the end of window 1 and again at the start of window 2 → up to 2× the rate in a moment. Attacker-triggerable by timing to the boundary. Fix with sliding window counter/log, or keep the previous window's count and weight it.
12Sliding window log — how does it work and what does it cost?accuracy vs memory
Sorted set of accepted timestamps; drop entries older than the window, count the rest. Exact, but memory is O(requests in window) — quantify it (~48 MB per hot key at 10k/s over 60s). Use where a hard boundary matters: login, payments.
13Sliding window counter — how does it approximate?the practical middle
Estimate rolling count as current + previous × (1 − fractionElapsed). Two integers per key, no boundary burst, not exact. Keep 2–3 sub-windows if you need tighter bounds. Admit the approximation out loud.
14Why is token bucket the industry default for API gateways?real-world grounding
Real traffic is bursty, so a limiter must permit legitimate bursts; bucket state is two numbers per key (scales to millions of identities); and the two knobs map cleanly onto product concepts (burst ceiling, sustained rate). AWS API Gateway, Stripe and most LLM APIs ship token bucket semantics.
15How do you pick between sliding log and token bucket?tradeoff reasoning
Ask whether the limit is a security/billing boundary (exactness required → log) or a protective throughput cap (average is enough → bucket), then compare the memory numbers against your traffic. Say the memory math out loud.
16Weighted requests — a search costs more than a ping.extending the model
Make cost a parameter: tokens ≥ cost → allow and subtract cost. Works in token bucket and sliding counter directly. In fixed window and sliding log use a weighted counter. Also the hook for concurrency caps and cost quotas (dollars per day) in the same engine.
17How do you handle a sudden 10× traffic spike?overload specialisation
The limiter does not change; the policies do — per-customer budgets, lowered burst capacity, aggressive load shedding, and client-side adaptive throttling so clients slow down before the server has to say no. The limiter is the last line, not the first.
18Which algorithm gives the smoothest output?one-liner check
Leaking bucket (queue drained at a fixed rate). Sliding log is also smooth but still admits whatever fits inside the window; it does not pace requests.
19Why does fixed window still get used in production?pragmatism
Because some limits are entitlements, not protections: "1000/day" with a calendar reset. Boundary precision is irrelevant there, and one counter per key is the cheapest thing that can possibly work.
20How would you implement this in the LLD version of the question?SDE-1 round
A RateLimiter interface with a Strategy per algorithm behind a factory, a KeyStrategy for identity extraction, a Storage interface (in-memory map now, Redis later), and a middleware that returns the 429 envelope. Then say which SOLID principle each extension honours — new algorithm = new strategy, no edits to existing code.

C · Distributed design and atomicity (21–33) where SDE-2 is won

21How do you rate limit across 50 app servers?the core distributed question
Shared state in Redis keyed by identity; every server reads and writes the same bucket. Stateless limiter service, stateful store. Local in-memory counters are wrong here — each server would grant its own quota, so effective limit = limit × servers.
22Why not just use an in-memory Map?the most common mistake to avoid
It is per-process state: N servers = N× the limit, plus restarts and deploys reset every user's quota. Fine for LLD/single process, wrong for distributed. Say this before the interviewer does.
23How do you avoid a race condition on the counter?atomicity — expect a follow-up
Check-and-decrement must be indivisible. GET then INCR is a TOCTOU race: concurrent requests both read the same value and both pass. Fix with a Lua script / Redis Function executed atomically inside Redis, in a single round trip.
24Why a Lua script and not a lock?mechanism choice
Redis executes a script atomically on its single thread, so you get the guarantee without a lock service, lock expiry, or an extra network hop. A distributed lock adds a failure mode and latency to buy something Redis already gives you for free.
25What if the counter needs to span multiple keys (per-IP AND per-user)?cluster subtlety
One script evaluating all tiers and returning the first violation. On Redis Cluster the keys must hash to one slot — use a hash tag like rl:{tenant}:user:42 so related keys co-locate. Cross-slot operations are not the same atomic unit and can partially apply.
26Redis is single-threaded — is that a bottleneck?capacity reasoning
At limiter volumes, no: Redis handles hundreds of thousands of ops/s per node, and one script is ~0.1–1 ms. You would be at 12k ops/s in the worked example. Shard by key across the cluster; if you exceed that, you have a design problem, not a threading problem.
27How do you handle clock skew across servers?correctness under NTP
Never trust per-node clocks for the decision: pass a single now in (or read Redis TIME) so all arithmetic uses one time source, and clamp negative elapsed to zero so a backwards NTP step cannot mint tokens or lock a user out permanently.
28How do you avoid unbounded memory?key cardinality attack
TTL every key (a token bucket can be deleted once a full refill has elapsed), cap how many identities you will track, and prefer a stable identity (user/API key) over IP. An attacker rotating IPs is a key-explosion attack.
29One tenant is 10% of traffic. Problem?hot keys / noisy neighbour
Hot shard: hash-tag by tenant means all of their traffic hits one slot. Options: sub-shard the bucket key by a hash of identity, give whales a dedicated bucket/shard, or move them to a separate limiter tier with its own budget. Also worth asking whether they should get a negotiated limit instead.
30Multi-region — where does the counter live?global vs regional limits
Decide which limit is global and which is regional. Regional Redis per-DC keeps latency low and survives a region outage; a truly global limit needs one authoritative store (cross-region latency, and availability becomes coupled to that region). A common design: hard global cap with generous regional budgets underneath.
31How would you deploy this without a maintenance window?operational maturity
Limits as configuration data pushed to the limiter service, versioned and hot-reloadable, not baked into a deploy. Shadow mode for new policies: count and alert without rejecting. Then enable per-tenant percentage rollout.
32What would you monitor?operability
Allow vs reject rate per scope and per limit, Redis latency and error rate, key cardinality, saturation ratio (Remaining/Limit distribution), and a rejection-reason breakdown. Alert on sudden reject-rate spikes — that is either an attack or your own config change.
33How would you load test this?verification instinct
Replay production-shaped traffic at 2–5× peak against the limiter in isolation and assert the accepted rate matches the configured rate within tolerance, plus a concurrency test proving no over-admission under parallel load on one key (the race). Verify the rejection path too, not just the happy path.

D · Client contract and failure behaviour (34–43) real-world polish

34What should the 429 response contain?contract design
Status 429 (RFC 6585), Retry-After with an honest value, the limit that tripped (RateLimit-Limit/-Remaining/-Reset on every response, not just the 429), the scope, and a machine-readable body — application/problem+json per RFC 9457 is the modern shape.
35Which headers, exactly?name them
IETF draft names RateLimit-Limit, -Remaining, -Reset (Reset is epoch seconds, never a duration); Retry-After takes precedence when both are present; legacy X-RateLimit-* is still common. Send them on success too so clients can self-throttle before being rejected.
36Should the client retry? How?symmetry
Only idempotent operations, or writes carrying an idempotency key. Honour Retry-After, add 10–30% jitter so a fleet does not resynchronise, cap total attempts (≈5), and pre-emptively slow down when Remaining/Limit < 10%. Exponential backoff with jitter, never a fixed sleep.
37Redis goes down. Now what?the key failure question
Decide per endpoint class and write it down: fail open for reads/feed (availability first, plus a local fallback limiter so you still have some protection), fail closed for anything that costs money or mutates state (payments, login, signup). Bound the Redis call with a short timeout so the limiter itself is never the outage; alert on the degraded path.
38Rate limit or circuit breaker — what is the difference?concept boundary
A limiter caps rate by policy; a breaker stops calling a failing dependency after a threshold (and is about failure, not fairness). They compose: limiter protects capacity, breaker protects you from a sick downstream. Neither replaces load shedding under overload.
39How do you stop a retry storm?cascade prevention
Client-side: jitter + exponential backoff + attempt cap. Server-side: a retry budget — cap the fraction of requests that may be retries (≈10%) and attempts per request (≈3), count retry ratio in load-shedding decisions, and make Retry-After accurate so correct clients need few retries.
40Thundering herd at a window boundary?classic failure
Yes for fixed window: everyone retries at the reset instant. Fix with sliding window, jittered/ incremental resets, and client-side backoff — or for a bucket, the refill is naturally gradual so there is no cliff.
41Should clients be allowed to bypass or raise their own limit?abuse thinking
No — client-side limiting is advisory and trivially bypassed; the server is the only enforcement point. What you can offer is a negotiated, higher limit tied to a plan/API key, so growth does not require a code change.
42Legitimate users keep getting 429s. Debugging order?troubleshooting
Check the scope that tripped (they may be behind a shared NAT so it is really the IP limit) → check whether a config change or deploy reset state → check key TTL/cardinality → check for clock skew → check whether a hot key inflated the shard. This requires the per-scope dashboards from Q32.
43How do you charge for overage?monetisation tie-in
Quota rather than rate: track cumulative volume (tokens/day, dollars) in a counter, warn at 80% and 100% with email, and allow upgrade or an overage price. Hard-throttle only after the quota, and use a distinct status where it is a billing condition.

E · Depth, trade-offs and senior framing (44–50) L5+ territory

44Given $X/month, where would you cut cost in this system?cost design — senior filter
Cost centres: Redis memory (the big one — state grows with active identities), limiter service CPU, and network hops. Levers: fewer active identities (idle TTLs), smaller buckets/more aggressive expiry, coarser algorithm where accuracy is not needed, sampling for analytics (you do not need to count every request to alert on abuse), and regional limiter instances to cut cross-region latency and egress.
45Is a limiter the right tool for preventing a scraper?tool selection
Partly. A limiter caps throughput, which raises the cost of abuse but does not identify it. Real defence layers authentication and authorisation, per-account quotas, anomaly detection on access patterns, and WAF/bot scoring. Say that, then place the limiter as the cheap first line.
46How does this change with 1000× traffic?scale headroom
Sharded Redis (key-space or hash-tag by tenant), the limiter service scaled horizontally behind an LB with no local state, and crucially an algorithmic question: at that volume, do you still need per-request checks, or can you move to periodic/quota accounting with burst tolerance? Also: shed load before the limiter, and cache the decision briefly to cut Redis round trips.
47How would you make the limit global across regions?distributed systems depth
One authoritative store for the global counter — accepting cross-region latency on the decision path, or a partitioned scheme where each region enforces a share of the global budget (fast, but a region can exceed its share during a failover). Trade regional latency budget vs global correctness; for most APIs regional budgets are the right answer.
48What if two regions both reject a legitimate user?failure interaction
Availability coupling: a global store's outage becomes everyone's outage. Mitigations — regional budgets with a global reserve, fail-open to the regional budget when the global store is unreachable, and explicit alerting on the degraded path. Decide this deliberately, do not discover it in an incident.
49Where does rate limiting sit relative to auth and caching?ordering in the pipeline
Order matters and is a real design decision: identity resolution (auth) must precede user-keyed limits; you often want a cheap IP limit in front of auth to protect the auth endpoint itself; a cache hit is cheap so some designs exempt cache hits or limit them separately; and logging/metrics must not be dropped for rejected requests or you cannot debug the rejections.
50How do you know your limiter is correct?verification, closing the loop
Three properties, each testable: (1) no over-admission — under concurrency, accepted rate never exceeds the configured rate (race-free by construction via atomic script); (2) correct wait — Retry-After is honoured by an independent client implementation; (3) graceful degradation — with Redis killed, the stated fail-open/closed policy is what actually happens. Test all three, and test the rejection path, not just the happy path.

14What you must know

The checklist. Everything below is examinable, and nothing above it is optional reading.

  • Token bucket: capacity vs refill rate, lazy refill with no timer, per-request cost weighting
  • Leaking bucket: FIFO queue, smooths output, adds latency, needs an overflow policy
  • Fixed window: the 2× boundary burst, and the weighted two-window fix
  • Sliding log: sorted set, exact, memory O(requests in window) with the number quantified
  • Sliding counter: the weighted approximation formula, and admitting it is approximate
  • Rate vs quota vs concurrency — three separate dimensions
  • Layered scopes: per-IP → per-user → per-tenant → global; first to trip wins and is reported
  • Placement: client (advisory) vs app middleware vs gateway; blast radius of each
  • Atomicity: TOCTOU race in GET-then-INCR; Lua script / Redis Function as the fix
  • Redis Cluster: hash tags so multi-key scripts stay single-slot
  • One time source; clamp negative elapsed (clock skew)
  • TTL + key-cardinality control; hot/whale keys
  • 429 + Retry-After + RateLimit-* (IETF draft names) on every response; Retry-After precedence; RFC 9457 body
  • Client behaviour: idempotency key on retried writes, jittered backoff, attempt cap, pre-emptive slowdown
  • Fail-open vs fail-closed per endpoint class, with a local fallback and a bounded timeout
  • Retry storms, retry budgets, thundering herd at reset
  • Limiter vs circuit breaker vs load shedding vs backpressure
  • Back-of-envelope: QPS from DAU, and the memory difference between bucket (O(keys)) and log (O(traffic))
  • Observability: per-scope saturation, reject reasons, Redis latency, shadow mode before enforcing
