## Checklist: Topics to Ace Google Technical Interviews

Based on the comprehensive review of all official materials, here is the master checklist of topics and strategies you must master to ace technical interviews at Google:

### 1. Data Structures & Algorithms Mastery
- [ ] **Core Structures:** Hash Maps, Trees (Binary, BST, Trie), Graphs, Linked Lists, Stacks, Queues.
- [ ] **Core Algorithms:** BFS/DFS, Binary Search, Dynamic Programming, Sorting algorithms.
- [ ] **Common Patterns:** Two Pointers, Sliding Window, Backtracking, Divide and Conquer.

### 2. The Coding Interview Execution Framework

![Coding Interview Flow](../assets/diagrams/coding-flow.svg)

- [ ] **Clarify Constraints:** Never start coding immediately. Ask about input sizes, data types (negative numbers, floats?), memory constraints, and edge cases.
- [ ] **State Assumptions Out Loud:** Speak your thought process. If you assume an array is sorted, or that it fits in memory, say it.
- [ ] **Brute Force Baseline:** Quickly articulate the naive solution to get a baseline before jumping into optimization.
- [ ] **Big-O Analysis & Trade-offs:** Always analyze Time ($O$) and Space ($O$) complexity. Explain the trade-offs (e.g., using a Hash Map to trade space for time).
- [ ] **Self-Testing:** Always dry-run your code with an example, especially checking for off-by-one errors and edge cases (empty inputs, zero, maximum values).

### 3. System Design & Architecture (HLD)

![System Design Flow](../assets/diagrams/sys-design-flow.svg)

- [ ] **Scope the Problem:** Define functional vs. non-functional requirements. Ask about Read/Write ratio, expected QPS, and latency targets.
- [ ] **Component Design:** Load Balancers, API Gateways, App Servers, Distributed Caches (Redis), Databases (SQL vs NoSQL).
- [ ] **Scaling Strategies:** Database partitioning/sharding, consistent hashing, replication, and handling hot-spots.
- [ ] **Navigating Ambiguity & Trade-offs:** There is no single correct design. Success lies in articulating *why* you chose a specific technology over another (e.g., strong vs. eventual consistency, CAP theorem considerations).

### 4. Non-Technical / Behavioral (Googleyness)
- [ ] **The STAR Method:** Frame your answers using Situation, Task, Action, and Result.
- [ ] **Quantify Impact:** Discuss your achievements using measurable metrics.
- [ ] **Navigating Ambiguity:** Show how you handle situations where instructions are unclear or resources are constrained.
- [ ] **Collaboration & Failure:** Be honest about failures, focusing on what you learned and how you adapted. Google highly values psychological safety and blameless post-mortems.

### 5. Role-Specific Domains
- [ ] **Embedded SWE:** Bit manipulation, hardware constraints (memory, CPU, power), real-time operating systems (RTOS), hardware-software interfacing.
- [ ] **AI/ML:** Practical application of models, model evaluation metrics, managing training data, and articulating ML trade-offs.
- [ ] **Product/UX/Sales:** Stakeholder management, GCA (General Cognitive Ability), quantitative solutions, and user-centric process flows.

## How to solve a Google coding interview question

This video features a mock technical interview to demonstrate what a coding interview at Google looks like and how candidates should approach problem-solving.

### Interview Format & Logistics
- **Environment:** You won't have access to a compiler or IDE. Practice writing code in a plain text editor like Google Docs or on a whiteboard.
- **Syntax Errors:** Don't stress over minor syntax errors (like the exact substring method name). Pick one, inform the interviewer, and focus on the logic.
- **Goal:** The questions are often deliberately open-ended to see how you engage, state assumptions, and arrive at an optimal solution.

### The Mock Interview Question
**Problem:** A farmer wants to find the maximum area of a square of good land they can farm. The land is represented as a 2D matrix of `1`s (good land) and `0`s (bad land). 

### Step-by-Step Candidate Approach
1. **Clarification and Assumptions:** 
   - The candidate first reads the question and asks clarifying questions, such as whether the area must be a square or if a rectangle is allowed. (Interviewer confirms it must be a square).
2. **Brute Force Solution (Naive Approach):**
   - The candidate explains a naive solution: looping over every position `(i, j)` and starting another nested loop to check for the maximum valid square of `1`s extending to the right and bottom.
   - The time complexity of this approach would be `O(N^4)`, which the candidate correctly identifies as non-optimal.
   - *Tip:* Explaining the brute force approach is good to show your thought process, but immediately acknowledge its inefficiency and move towards a better solution.
3. **Recursive Solution:**
   - The candidate proposes a recursive algorithm. For each cell containing a `1`, recursively ask its right, bottom, and bottom-right diagonal neighbors for the size of the square they can form.
   - The base case returns `0` if the cell is a `0`.
   - If the cell is `1`, its square size is the minimum of the three neighbors' values, plus `1`.
   - While better, basic recursion may result in redundant calculations unless optimized with memoization.
4. **Dynamic Programming (Bottom-Up) Solution:**
   - Guided by the interviewer, the candidate develops an optimal `O(N*M)` bottom-up DP solution.
   - A DP matrix of the same dimensions is initialized with all zeros.
   - Iterate through the input matrix. If a cell contains a `0`, skip it (DP cell remains `0`).
   - If a cell contains a `1`, look at the already-computed DP values of its top, left, and top-left diagonal neighbors.
   - Update the DP cell with: `min(left, top, diagonal) + 1`.
   - The maximum value written in the DP array represents the side length (height) of the largest square.
5. **Implementation Details:**
   - The candidate writes Python code.
   - They handle boundary conditions correctly (edges don't have left/top neighbors).
   - They optimize space slightly by maintaining a `max_num` variable to keep track of the maximum square found during the main iteration, rather than doing a second pass over the DP array at the end.

### Key Takeaways for Candidates
- **Think Out Loud:** Explain your decision-making and logic throughout the entire process.
- **Check Assumptions:** Always explicitly state your assumptions and check if they align with the interviewer's expectations.
- **Collaborate:** Listen to the interviewer's hints. In this mock interview, the interviewer successfully nudges the candidate from recursion to a bottom-up DP approach.

## How to apply for a job at Google

This video walks candidates through the general hiring process at Google and offers practical advice on how to successfully apply.

### 1. Finding the Right Role
- **Search:** Browse the career site at [careers.google.com](https://careers.google.com). Use the search tool to input who you are, what you do, and where you would like to work.
- **Career Profile:** Create a career profile to receive customized job recommendations and alerts for new openings that match your background.
- **Limits:** Keep in mind that you can apply for a maximum of 3 jobs every 30 days.
- **Qualifications:** Ensure you meet *all* the minimum listed qualifications before submitting your application.

### 2. Preparing Your Resume / CV
- **Tailor Your Resume:** Make a copy of your standard resume and heavily tailor it to the specific job description you are applying for. Align your skills with the role's requirements.
- **Highlight Projects:** Be specific about the projects you have worked on or managed. 
- **The Google Formula:** Use the standard framework: *"Accomplished X as measured by Y, by doing Z."*
- **Quantify Impact:** Use metrics and numbers to quantify your work so recruiters can understand the scale of your accomplishments.
- **Length:** Keep it short. One page is ideal, though two pages are acceptable for highly experienced candidates.
- **Cover Letters:** Most roles do not require a cover letter unless explicitly stated in the job description.

### 3. The Hiring and Assessment Process
- **Initial Review:** If your resume matches the role, a recruiting team member will reach out. If you haven't heard back within 8 weeks, the team has likely moved on for that specific role, but you remain in the system for potential future matches.
- **Assessments:** Depending on the role, the process may include coding quizzes, short chats with a recruiter/manager, or samples of hypothetical project work.
- **No Brainteasers:** Google no longer uses tricky brainteasers. All questions are designed at face value to assess your past work experience and how you approach unfamiliar problems.
- **Rubrics:** Your answers are evaluated against standardized rubrics to accurately gauge your strengths and teamwork capabilities.

### 4. Interview Accommodations
- The recruiting team is fully prepared to provide accommodations such as sign language interpreters, specialized equipment, interview breaks, or extended time.
- Simply inform your recruiter about your needs—no detailed medical or personal information is required. They will connect you with the candidate accommodations team.

### 5. Final Review and Next Steps
- **Review:** After interviews, your application packet is reviewed by multiple Googlers at various levels.
- **Offer:** If everything is approved, the recruiter will extend an offer.
- **Future Opportunities:** If you aren't selected, do not get discouraged. Many current Googlers applied to multiple roles before getting hired. Your profile is saved, making future applications much easier.

## How to prepare for Google’s technical interview questions

This video outlines what to expect in a Google technical interview and provides a comprehensive guide on exactly what subjects to study and how to perform during the interview.

### Interview Logistics
- **Format:** Most interviews take place virtually via Google Meet.
- **Setup Needs:** A compatible computer/laptop, a webcam, a backup phone (for audio/video issues), and a method for taking notes and sharing code (e.g., a shared Google Doc).
- **Dress Code:** Everyday casual clothes are fine—essentially what the interviewer will be wearing.
- **Accommodations:** Candidates can easily request accommodations (e.g., interpreters, breaks, extended time) directly through their recruiter without providing extensive details.

### What to Expect in the Interview
- **Variety by Role & Level:** Interviews vary based on the specific role (e.g., SRE vs. Machine Learning) and seniority. Senior roles require deeper subject matter expertise.
- **Generalist vs. Specialized:** You will likely have at least one interview focused on generalist skills and one on specialized skills.
- **Environment:** You will not use a compiler or IDE. You must write prototype code in a shared document, on a whiteboard, or on paper.

### Core Preparation Areas
You will be tested on computer science principles, problem-solving skills, and coding fluency. Key topics to study include:

#### 1. Coding & Algorithms
- Code efficiently in your language of choice.
- Understand time (Big-O notation) and space complexity and how to improve them.
- Be able to find corner and edge cases.

#### 2. Testing
- Know how to unit test your code and brainstorm interesting inputs or test cases.
- For system design, understand end-to-end integration, load, performance, and security testing (e.g., for a system like Gmail).

#### 3. Data Structures
- Have a solid grasp of fundamental structures: Arrays, Hash Tables, Linked Lists, Graphs, Trees, Stacks, and Priority Queues.

#### 4. Mathematics & Quantitative Skills
- Refresh your knowledge of elementary probability theory and combinatorics.
- Understand counting problems and N-choose-K scenarios.

#### 5. Graphs
- Know the three basic ways to represent a graph in memory: Objects & Pointers, Matrix, and Adjacency List (including their pros and cons).
- Understand traversal algorithms: Breadth-First Search (BFS) and Depth-First Search (DFS), their complexity trade-offs, and how to implement them.
- Be familiar with graph algorithms for distance, search, connectivity, and cycle detection.

#### 6. Advanced Computer Science Concepts
- **Recursion & Dynamic Programming:** Practice thinking recursively and coding recursive solutions. Be careful to approach them properly as they can be tricky.
- **NP-Complete Problems:** Familiarize yourself with classic problems like the Traveling Salesman and the Knapsack problem so you can recognize them if asked.

#### 7. System Design & Architecture (Particularly for experienced candidates)
- **High-Level Design:** Understand distributed systems, interfaces, robustness, limitations, and trade-offs.
- **Operating Systems:** Study processes, threads, concurrency issues, locks, mutexes, semaphores, and monitors. Know how context switching works at the OS and hardware levels.
- **Concurrency Pitfalls:** Understand Deadlock and Livelock and how to avoid them. Know what resources a thread vs. a process needs.
- **The Internet:** Understand how the internet works at a high level.

### Best Practices During the Interview
- **Think Out Loud:** Explain your thoughts, clarify your answers, and show your work. The interviewer evaluates your problem-solving process as much as the final code.
- **Check Assumptions:** Verbalize your assumptions and ask clarifying questions. Many questions are intentionally vague to see how you engage with the problem.
- **Iterate and Improve:** Don't just settle for a brute-force approach. Present your initial thoughts, then refine and optimize your solution for better efficiency.
- **Practice:** The best preparation is writing code without an IDE. Find problems, write solutions, test them manually for bugs, and do mock interviews with friends to practice your pacing.

Non-technical interview questions are used across all roles at Google to assess how candidates approach and solve problems.

- **Setup Requirements:** Ensure you have a compatible computer or laptop, a working webcam, and a backup phone in case you experience audio or video issues.

## How to prepare for a System Architecture Interview for Embedded SWE

This video features Ching (a Google recruiter) and two Google engineers (Mao and Kitty) explaining and demonstrating the System Architecture technical interview process, with a specific focus on Embedded Software Engineering.

### Interview Process & Key Principles

1. **Clarify the Problem:**
   - Questions are intentionally open-ended.
   - Proactively ask questions to define the problem's core, details, and scope (Problem Scoping).
   - Propose assumptions and align your understanding with the interviewer.
2. **Identify Key Components:**
   - **High-Level Architecture:** Outline a top-down structural blueprint of the system, detailing workflows and steps before diving into detailed code.
   - **Deep Dive & Technical Depth:** Explore specific modules in depth. The interviewer evaluates your domain knowledge, your ability to optimize solutions, and your handling of potential system issues/abnormalities (Corner Cases).
   - **Trade-offs:** Explain the pros and cons of different options and defend your design decisions. Be prepared to back choices with mathematical calculations or quantitative analysis.
3. **Ensure Reliability and Scalability:**
   - **Reliable:** The system must handle errors and failures (e.g., data loss, component failure) without service interruption, ensuring data consistency and incorporating preventative measures.
   - **Scalable:** The system should handle increasing loads (users, data) via horizontal/vertical scaling and performance optimization. Start with a basic solution and evolve it into a scalable version.

### Essential Interview Techniques
- **Think Out Loud & Interact:** Verbalize your thoughts continuously. 
- **Ask Questions:** Clarify doubts or get hints when stuck instead of remaining silent.
- **Time Management:** Efficiently balance breadth and depth within the time limits.
- **Tool Usage:** Be proficient in Google Docs and Google Drawings to map out designs.

### Mock Interview Scenario: Pixel Phone OTA Update Design
The candidate is tasked with designing an Over-the-Air (OTA) update system for Pixel phones, supporting 7 years of updates.

- **Clarification:** The candidate clarifies they are designing the end-to-end process (not just post-download) and confirms they should initially assume downloads succeed but updates might fail. They suggest update frequency should match Android releases to save server cost, reduce testing burden, and maintain a good user experience, with faster updates reserved for critical (security/privacy) bugs.
- **Handling Failures:** To handle failed updates, the candidate proposes an **A/B Partition** method. The phone downloads updates to an inactive partition (e.g., B while running on A) and boots from B upon restart. If B fails, it reverts to A. 
- **Corner Cases:** If reverting to A also fails, the device falls back to the Bootloader/Recovery mode.
- **Security:** To prevent malicious software, updates must come solely from the Google Server, signed with a Private Key, and undergo integrity checks on the device.
- **Storage Optimization:** Instead of doubling storage for A/B partitions, the candidate introduces the **Overlay** method (Virtual A/B), where only incremental differences ("sticky notes") are written to the current partition.
- **Package Size Optimization:** For frequent, smaller updates, the candidate suggests using the XOR method on data differences, creating many zeros to maximize compression and reduce package size.

## How to prepare for a Coding Interview for Embedded SWE

This video features Amanda (a Google Recruiter) and two Google software engineers (Blossom as the interviewer, Michelle as the candidate) discussing and demonstrating the expectations for an Embedded System Coding interview. 

### Core Evaluation Elements & Process
The Embedded System Coding interview focuses on the close interaction between software and hardware, emphasizing code efficiency, reliability, and hardware constraints. 

1. **Clarify:** 
   - Proactively ask questions to refine open-ended problems, define boundaries, and find edge cases. 
   - Examples of clarifications: input data types, array ranges, output formats, etc.
2. **Assume:**
   - Clearly state your assumptions (e.g., using specific standard library APIs). This builds consensus and prevents your solution from deviating from the interviewer's expectations.
3. **Describe your solution:**
   - Discuss your approach before implementing it. Start with the simplest, most intuitive approach for a basic case, ensuring the interviewer agrees. Discuss Time and Space Complexity.
4. **Implement:**
   - Write clean, executable code. Good readability and clear variable names are crucial because they reflect your teamwork abilities.
   - Consider boundary conditions and handle exceptions (corner cases).
5. **Iterate:**
   - Optimize the initial workable code based on interviewer prompts. Address increased complexity (e.g., handling larger datasets or multiple variables).
   - Discuss trade-offs, like sacrificing space complexity to improve time complexity.

### Mock Interview Scenario: Button Debounce using GPIO
The candidate is tasked with implementing a physical button controlled via GPIO, including a debounce mechanism to filter out signal noise when the button is pressed or released.

- **Clarification:** The candidate asks if there are multiple buttons (just one), defines debounce as brief signal noise during state transitions, checks if the GPIO is dedicated (yes), sets the debounce threshold (50ms), and asks if the GPIO triggers an interrupt or requires polling (interrupt). The interviewer also permits the use of a hardware timer.
- **Solution Design:** The candidate proposes a state machine:
  - Trigger an IRQ on rising/falling edges.
  - On an IRQ trigger, set a 50ms timer. If another IRQ happens before timeout, cancel and reset the timer.
  - If the timer times out, check if the state actually changed. If yes, trigger the callback; if it’s the same, do nothing.
- **Implementation Details (Linux Driver approach):**
  - Uses a struct to encapsulate button data (GPIO, IRQ number, state, callback function pointer, `hrtimer`), ensuring modularity and readability.
  - `debounce_init()`: Initializes the GPIO and IRQ.
  - `button_handler()`: Acts as the Interrupt Service Routine (ISR). Cancels any active timer, reads the new GPIO state, and resets the timer if a change is detected.
  - `timer_handler()`: Called on timeout to confirm the stable state and execute the callback.
  - `debounce_exit()`: Disables IRQ, clears GPIO, resets the timer, and frees memory.
- **Optimization & Edge Cases:** 
  - **Context Issue:** The candidate realizes `timer_handler` runs in an interrupt context and calling the callback might cause a sleep, crashing the system. To fix this, they use a Linux `workqueue` (delayed work) to offload the callback to a thread.
  - **Concurrency Issue:** The candidate identifies that `button_handler` and `timer_handler` might run simultaneously. They implement a `spin_lock_irqsave()` and `spin_unlock_irqrestore()` to protect the shared state and prevent deadlocks in the interrupt context.

## Recruiter tips: Understanding Google's interview process

This video features Simran, a recruiter at Google's New York City office, offering tips on understanding Google's unique interview style and building strong solutions to interview questions. Google interviews generally feature two formats of questions:

### 1. Hypothetical Questions
These questions typically start with phrases like "imagine you are..." and present a hypothetical scenario for you to solve. They assess problem-solving and critical thinking skills in real-time.

**Tips for Hypothetical Questions:**
- **Understand the problem:** Identify the core challenge and ultimate objective. Don't hesitate to ask clarifying questions to gather all the information needed to build a viable solution.
- **Think out loud:** Walk the interviewer through your thought process as you build the solution. Discuss the factors you are considering, such as stakeholders, timelines, pros and cons, budgets, and data.
- **Present a thorough solution with a rationale:** Explain *why* you chose your solution. Relate your decision back to the core problem and share the insights that led to your choice.

These questions typically start with phrases like "tell me about a time when..." and require you to provide real-life examples from your past professional experience to showcase your skills in action.

**Tips for Behavioral Questions:**
- **Use the STAR Method:** To deliver a structured and impactful response, format your answer using Situation, Task, Action, and Result. This framework ensures you clearly communicate the scope, context, and ultimate impact of your past contributions.

### General Preparation Advice
- **Practice extensively:** Practice your delivery beforehand. Simran recommends using AI tools like Gemini Live to simulate live interviews and receive on-the-spot feedback, which helps refine your responses and boosts confidence for interview day.

## Google India Engineers in a Mock Coding Interview

This video demonstrates how a Google engineer approaches an engineering problem during a coding interview. The mock interview features Swati (Software Engineer) as the interviewer and Ashwatha (Hands-On Software Engineer, Java/C++) as the candidate.

### The Problem
You are given a collection of numbers and a target number. You need to find a pair of numbers in the collection which sums up to the given target.

**Examples:**
* Collection: `[1, 2, 3, 9]`, Target: `10` -> Pair exists (`1` and `9`).
* Target: `8` -> No pair exists.

### Step-by-Step Approach

**1. Clarifying Questions**
Before jumping into coding, Ashwatha asks several clarifying questions:
* **Possibility of no pairs:** Can there be cases where no pair adds up to the target? *(Yes)*
* **Data scale and format:** How is the data provided? Will it fit in memory? Is it an array? *(Yes, in memory, consider it an array)*
* **Handling duplicates:** Can the same number be reused (e.g., adding `4` to itself to get `8`)? *(You cannot use the same index twice, but there can be repeating numbers in the array)*
* **Data types:** Are they integers only? Any negative or floating-point numbers? *(Integers only, can be negative, no floating points)*

**2. Solution 1: Brute Force**
* **Method:** Iterate with two indexes (`i` and `j` where `j = i + 1`) through the array, check all pairs.
* **Complexity:** O(N^2) (Quadratic).
* **Feedback:** Not very efficient, interviewer asked for a better approach.

**3. Solution 2: Binary Search (assuming sorted array)**
* **Method:** Iterate through the array. For each element, find its complement (`target - element`) using binary search in the remaining array.
* **Complexity:** O(N log N).
* **Feedback:** Interviewer asked if it can be done in linear time.

**4. Solution 3: Two Pointers (assuming sorted array)**
* **Method:** Place one index at the start (`low = 0`) and one at the end (`high = array size - 1`). If the sum of elements at both indexes is greater than the target, decrement the `high` index. If the sum is less than the target, increment the `low` index. Stop when a pair matches or the pointers cross.
* **Complexity:** O(N) (Linear).
* **Implementation:** Ashwatha successfully coded this in C++, choosing to return a Boolean (`true` if found, `false` otherwise) based on discussion with the interviewer. Handled edge case of empty vector automatically.

**5. Follow-up 1: What if the collection is unsorted?**
* **Initial thought:** Sort it first (would become O(N log N)).
* **Optimized Solution:** Use a Hash Set (C++ `unordered_set`).
* **Method:** Iterate through the array. For each element, check if it exists in the set of "needed complements". If it does, return `true`. If not, calculate its complement (`target - element`) and insert it into the set.
* **Complexity:** O(N) (Linear).
* **Implementation:** Coded using `unordered_set` and trace-tested it step-by-step with an example array.

**6. Follow-up 2: What if the collection has millions of numbers (won't fit in memory)?**
* **Method:** Distributed processing. Break the range of values into bounded subranges/chunks and process them across multiple computers to compute the hash sets of complements.

### Tips and Best Practices Mentioned
* **Clarify the problem:** Ask clarifying questions to ensure you understand the problem (e.g., asking about floating-point numbers). Feel free to ask the interviewer to repeat or write the question down.
* **Think out loud:** Always articulate your thought process. It helps the interviewer understand your approach and course-correct you if needed.
* **Brainstorm collaboratively:** Treat the interviewer as a partner.
* **Start simple:** It's okay if your first solution isn't the most optimal. Articulate a simple solution, and let the interviewer challenge you to improve it.
* **Test your solution:** Dry-run your code using the provided examples or your own examples.
* **Check edge cases:** Test with scenarios like empty collections to gain confidence in your solution.

## Google India Engineers in a Mock System Design Interview

This video features a mock system design interview. Abhijit (Engineering Manager) acts as the interviewer and Divya (Staff Software Engineer in Data Engineering) as the candidate.

### The Problem Statement
Design a system to report on the top and most listened to songs and albums (by user, country, day, month, year). You are given a tracking API that captures when a user listens to a certain song in an album.

### Step-by-Step Approach

**1. Clarifying Questions & Assumptions**
Divya begins by defining the scope, use cases, and scale:
* **Scope:** No personalization needed. Mobile/browser user experience is out of scope.
* **Scale Assumptions:** 400 million unique users, with ~40% active (let's say 200 million). On average, 2 hours of listening per day per active user. 70 million songs in catalog, growing by 60k daily. 
* **Throughput:** ~600 million song listening events per day.
* **Latency:** Batch processing is acceptable. Lists can refresh every 1 hour (configurable up to 1 day for less active regions).
* **Query Latency:** Starts at 200 QPS, but needs to scale up to 1000 QPS.

**2. High-Level Design (HLD)**
* A **Tracking API** receives events when a user listens to a song.
* The API writes events to a **Black Box** (Data processing unit).
* Other APIs query this Black Box to retrieve top 'N' results.

**3. Low-Level Design (LLD) & Component Details**
* **Queue:** To scale the Tracking API and prevent data loss during traffic peaks, events are immediately written to a distributed queue. Divya chose **Kafka** for its scalability and industry-proven reliability.
* **Batch Storage:** A streaming job reads from Kafka and writes to a Batch Store. Divya chose **HDFS** (could also be S3/GCS) due to its distributed, scalable nature for batch processing.
  * **Partitioning strategy:** Chose daily date partitioning over hourly to prevent creating too many small files in the HDFS namespace.
* **ETL & Data Enrichment:**
  * Raw event schema: `song ID`, `album ID`, `user ID`, `location`, `API credentials`.
  * An ETL pipeline processes these events and joins them with metadata (song and album data, copied to HDFS from an OLTP datastore via Change Data Capture).
  * Enriched schema: `timestamp` (date, hour), `user ID` (gender, age group), `location` (city, region), `song author`, `album genre`.
* **Aggregation & Serving:**
  * To avoid expensive on-the-fly aggregation, the pre-computed aggregations are run via an ETL or query engine (like BigQuery or Presto).
  * The computed results are dumped into an **RDBMS** for serving.
  * APIs directly query the RDBMS for fast, predictable performance since the data is relatively static between hourly batch runs.

**4. Reliability & Fault Tolerance**
* **Tracking API:** Placed behind Load Balancers across multiple regions. Provisioned with 100% capacity in both regions to prevent data loss if one region goes down.
* **Kafka:** Deployed across multiple regions.
* **Batch Processing:** Run primarily in Region 1, with Region 2 serving as a backup that can be booted up if Region 1 fails.
* **Database (RDBMS):** Replicated in both Region 1 and Region 2 for high availability.

**5. Additional Considerations (Discussed)**
If time permitted, the candidate would have focused on:
* Health checks and system monitoring alerts.
* Data quality checks (ensuring processed data matches expected formats without data loss).
* Recovery mechanisms (backfilling data to get back to a normal state after system restarts).

### Tips and Best Practices from the Interviewer
* **Methodical execution:** Start with high-level requirements, clearly state assumptions, build the high-level design, and then dig into low-level design.
* **Time management:** Spend the appropriate amount of time on LLD without getting bogged down in minutiae that overwhelm the interviewer.
* **Math skills:** Be comfortable doing back-of-the-envelope calculations for data and scale.
* **Think out loud:** Always talk through your thought process so the interviewer can follow along and guide you if necessary.
* **Receptiveness:** Take hints and nudges well. If the interviewer pushes you in a specific direction, change course accordingly.
* **Stay in scope:** Do not overcomplicate the design by attempting to solve problems the interviewer hasn't explicitly asked for.
* **Trade-offs:** Proactively discuss the pros and cons of different technologies or design choices.
* **Non-functional requirements:** Make sure to address scalability, high availability, security, and realistic resource expectations.

## How to: Work at Google — Example Coding/Engineering Interview

This video features a mock coding interview between two Google software engineers, Edgar (the candidate) and Becky (the interviewer), demonstrating the expected process and problem-solving strategies.

### The Interview Problem
**Task:** Given a collection of numbers and a target sum, determine if there is a matching pair within the collection that equals the target sum.
*   **Example 1:** Collection `[1, 2, 3, 9]`, Target `8` -> Result: `False` (No pair adds up to 8).
*   **Example 2:** Collection `[1, 2, 4, 4]`, Target `8` -> Result: `True` (4 + 4 = 8).

### Candidate's Process and Steps

**1. Clarifying Questions**
Before writing any code or devising an algorithm, the candidate asked several critical questions to understand the constraints:
*   How are the numbers stored? (Answer: In memory, in an array).
*   Are they ordered? (Answer: Assume they are in ascending order initially).
*   Are there repeating elements? (Answer: Same index can't be used twice, but the same number can appear twice in the array).
*   What is the data type? Are there negatives? (Answer: Integers, and negatives can occur).

**2. Brainstorming Solutions**
The candidate iterated through several solutions, improving efficiency each time:
*   **Approach 1: Brute Force.** Compare every single possible pair using nested `for` loops. Time complexity: Quadratic. The interviewer prompted for a more efficient solution.
*   **Approach 2: Binary Search.** Since the array is sorted, iterate through each number and perform a binary search for its complement (Target - Number). Time complexity: `O(N log N)`. Better, but the interviewer asked for faster.
*   **Approach 3: Two Pointers.** Maintain two pointers, one at the lowest value (start) and one at the highest (end). If the sum of the two values is too large, move the high pointer down. If too small, move the low pointer up. Stop when they cross or the sum is found. Time complexity: Linear `O(N)`. 

**3. Dry Run and Coding (Sorted Array)**
*   The candidate dry-ran the two-pointer logic with a visual example.
*   They clarified the return type (Boolean instead of indices for simplicity).
*   Wrote the solution in C++, actively thinking out loud and accounting for edge cases (like an empty array).

**4. New Constraint: Unsorted Array**
*   The interviewer introduced a twist: the collection is no longer sorted, but the solution still needs to be faster than `O(N log N)`.
*   **Approach 4: Hash Set.** The candidate devised a linear time and space solution using a hash set. 
    *   Iterate through the array. 
    *   Check if the current value is already in the hash set. If yes, a pair is found. 
    *   If no, calculate its complement (Target - Current Value) and store it in the hash set.
*   The candidate carefully dry-ran this to ensure it handled duplicate numbers correctly (checking the set *before* inserting).
*   Wrote the updated C++ code using `unordered_set`. Discussed time `O(N)` and space `O(N)` constraints.

**5. Follow-up Question: Scaling**
*   **Question:** What if there are 10 million integers and it doesn't fit in memory?
*   **Answer:** Process the input in chunks using parallel processing across multiple machines. Merge the hash sets carefully, accounting for cross-machine duplicates and making sure things stay accurate.

### Interviewer's Recap & Tips for Success
The interviewer highlighted why the candidate's performance was excellent:
1.  **Ask for Clarification:** Don't hesitate to ask questions to fully understand the scope, constraints, and edge cases (e.g. negative numbers vs. floating points).
2.  **Think Out Loud:** This gives the interviewer a window into your thought process. It allows them to course-correct you or ask follow-up questions that showcase your knowledge. Two minds are better than one.
3.  **Talk Before You Write:** Iterate through solutions verbally first. The first idea is rarely the most optimized. Finalize the logic before writing code down.
4.  **Test Your Solution In Real-Time:** Use provided examples or make up your own to dry-run the logic. Specifically, look out for edge cases (like an empty collection) and verify your code handles them correctly.
